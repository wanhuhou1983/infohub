# ADR-005: 数据采集架构——去中间件化的多源直连

- **状态**: Accepted
- **日期**: 2026-04-25

## 背景

InfoHub 需要从多种异构信息源采集内容，每个源的技术协议、访问方式、更新频率各不相同。初始版本通过 Miniflux（自托管 RSS 阅读器）统一管理 RSS 类源，但这种方式引入了两层间接性。

需要设计一个统一的采集架构，满足以下约束：
- 单机可运行（依赖越少越好）
- 每种信息源的采集逻辑独立（便于独立调试和扩展）
- 采集结果统一存入 PostgreSQL + OB Markdown
- 图片自动处理（下载 + COS 上传 + URL 替换）

## 决策选项

### 方案 A：统一中间件层（如 Miniflux + Webhook）

- 所有 RSS 源通过 Miniflux 订阅，Miniflux 的 Webhook 触发 InfoHub 采集
- 非 RSS 源（微信/B站/YouTube）各自独立
- 优点：RSS 源统一管理（更新/暂停/删除）
- 缺点：**需要额外部署 Miniflux**（Go 进程 + PostgreSQL）→ 多一个需要维护的服务；InfoHub 的源管理逻辑与 Miniflux 源管理逻辑可能冲突（用户需要在两个地方配置）

### 方案 B：多源直连 + 统一入库管道

- 每种信息源有独立的采集逻辑（Python 脚本 / TypeScript 函数 / API 调用）
- 所有采集结果通过统一管道入库：`fetch → parse → processImages → translate → save(DB+OB)`
- 优点：无外部依赖、每种源可独立优化、采集流程可精确控制
- 缺点：每种源需要独立实现解析逻辑、重复的样板代码

### 方案 C：消息队列 + Worker 架构

- 采集请求 → 消息队列 → Worker 执行采集 → 结果写回
- 优点：可水平扩展、支持重试和死信处理
- 缺点：**对于个人项目过度设计**；需要额外部署 RabbitMQ/Redis/NSQ

## 决策

**选择了方案 B：多源直连 + 统一入库管道**。核心结构如下：

### 各信息源的具体采集策略

| 来源类型 | 采集方式 | 实现位置 | 去重键 |
|---------|---------|---------|--------|
| **RSS** | `rss-parser` 直连 feed URL + MinerU 全文抓取 | `routes/fetch.ts` | `hashString(rss_${feedUrl}_${guid})` |
| **微信公众号** | WeFlow HTTP API 获取文章列表 + `wechat-article-spider` Playwright 抓取全文 | `routes/fetch.ts` + `scripts/` | `hashString(url)` |
| **新闻联播** | `cn.govopendata.com` 公开数据 → HTML 解析 | `routes/fetch.ts` | `hashString('xwlb_'+YYYYMMDD)` |
| **人民日报** | Python 脚本 `rmrb_daily.py --full` → paper.people.com.cn | `scripts/fetch_rmrb_to_ob.py` | `hashString('rmrb_'+YYYY-MM-DD)` |
| **B站** | Bilibili 官方 API + yt-dlp 字幕下载 | `routes/bilibili-admin.ts` | `hashString('bilibili_'+bvid)` |
| **YouTube** | YouTube Data API / 内建 RSS feed | `routes/youtube-admin.ts` | `hashString('youtube_'+videoId)` |
| **Twitter/X** | Nitter RSS（无官方 API Key） | `routes/twitter-admin.ts` | `hashString('twitter_'+tweetId)` |
| **播客** | 喜马拉雅/蜻蜓/小宇宙搜索API + RSS 播客音频 | `routes/podcast-admin.ts` | 同 RSS 去重 |
| **喷嚏图卦** | Python 脚本爬取 | `scripts/fetch_penti_to_ob.py` | 独立于主流程 |

## 理由

1. **去 Miniflux 减少运维负担**（`18a557f`，2026-04-25）：Miniflux 是一个独立的 Go 服务 + PostgreSQL，需要单独部署和维护。将其替换为 `rss-parser` 直连后，整个系统降为单服务（Hono）。这是"单机可运行"原则的关键决策。

2. **每种源独立实现更适配**：RSS 适合通用解析，但微信公众号需要 WCDB + Playwright 组合，B站需要 yt-dlp 处理字幕，Twitter 需要 Nitter 容错。统一抽象层反而会限制每个源的能力。

3. **统一管道保证数据一致性**：无论来源如何，`processImages → translate → saveArticleFile` 的处理顺序保证所有文章都经历相同的数据增强步骤。OB 侧（`saveArticleFile`）的 frontmatter 格式一致。

4. **去重键的多样性**：不同来源使用不同的去重键生成方式（基于 URL / 日期 / ID），每种方式都针对对应来源的 ID 稳定性设计。

5. **采集可独立触发**：每种源的采集逻辑对外暴露为 REST API 端点，既可由 `daily_fetch.sh` 定时触发，也可手动从管理面板触发。

## 后果

### 正面

- 单服务部署（Hono 搞定一切），运维极简
- 每种源可独立优化、独立修复、独立扩展
- 采集流程确定性强（无外部中间件故障链）
- Nitter RSS 方案让 Twitter 采集零 API 费用

### 负面

- 去 Miniflux 后失去了 RSS 源的统一管理界面（增/删/改需通过 InfoHub 自身的 sources 管理面板）
- 每种源需要独立处理认证/限流/错误重试
- 微信公众号采集依赖 WeFlow 中间件的可用性（需 Mac 客户端保持运行）
- Twitter 采集依赖 Nitter 实例的可用性（需要多级容错 fallback）
- 播客音频解密逻辑因平台而异（喜马拉雅/蜻蜓加密格式不同），无法标准化

### 每日采集流水线

`scripts/daily_fetch.sh` 按以下顺序依次执行：
1. RSS feeds（并行）
2. 新闻联播（每日新稿）
3. 人民日报（每日新稿）
4. 喷嚏图卦（每日新稿）
5. 公众号（增量）
6. B站/YouTube（更新 + 稍后再看）
7. Twitter（增量）
